01What this site is

The five-minute mental model. If you only remember one thing, make it the last paragraph.

masterconcept.ai is Master Concept's public marketing site: a WordPress install on SiteGround, fronted by Cloudflare, running the Hello Elementor theme with Elementor Pro and ElementsKit on top, translated into four languages by WPML.

Counts taken from the REST API, Nov 2026. Note how thin zh-hk and zh-cn are — that imbalance drives a lot of section 6.

Three kinds of page live here

Elementor pages legacy

Still the majority, and still what the live header and footer run on. Built visually; the layout is JSON in the database. You'll maintain these — you won't start new ones.

Native HTML the direction

Hand-written HTML + CSS in the page content, no Elementor, built from Figma with the skill. Exact, fast, reviewable. Section 8 and section 10.

Plugin-rendered

Lists, author pages and nav columns rendered by our own WP Buddy plugin through wpb_ shortcodes. Content comes from the database, not from markup.

Where we're heading — read this before you build anything

We are moving off Elementor and onto our own hand-built HTML, produced from the Figma design with the figma-to-wp skill. That is the direction for all new work.

So: new pages are native HTML, not Elementor. Elementor stays for the hundreds of pages already built in it, and it is still what the live header and footer run on — but it isn't where you start. If you're about to open the Elementor editor to build something new, check first.

Why we're moving: Elementor layouts live as JSON in the database, so they can't be reviewed, diffed or version-controlled, they're slow to load, and matching a Figma design inside a visual builder is guesswork. Native HTML is exact, fast, and reviewable before it ships. Sections 8 and 10 are the how.

The one thing to remember

There is no staging site. Every change you make is on production, visible to the public the moment the cache clears. Work locally, review locally, then push — and always know which of the four languages you are editing.

No FTP, no server access

You won't need either. The repo deploys itself — push to main and GitHub Actions syncs your WP Buddy change onto the live site. That's the whole deployment story for plugin code, and it's why repo access is the one credential that reaches production.

Where passwords go

Two different things, and it's worth keeping them straight:

Shared team logins

Magic Login. You sign in as yourself and it hands you the shared account — Claude's mc-marketing among them. You never see or store the password.

Your own credentials

Keep them in a password manager, never a text file or a note. The company runs 1Password — ask Tommy whether you get a seat. Bitwarden is a solid free alternative if you'd rather run your own.

Credential rules — no exceptions
  • A password lives in a password manager and nowhere else. Never in code, never in a commit, never in a ticket, never pasted into a chat.
  • The plugin reads every key it needs from the WordPress database at runtime — so there is never a reason to hardcode one.
  • If you think you need a credential in a file, ask first. There's almost always an existing helper.

06Languages & WPML

Four languages, uneven content, and a translation layer with sharp edges. This section exists because each of these cost us a day.

Trap 1 — fallback goes to English only

WPML falls back to the default language and nowhere else. There is no chain. A missing zh-hk page does not fall back to zh-hant, which is what a Hong Kong reader would actually want — it falls back to English.

Where we need 香港 → 繁中 → English, we build that chain ourselves in the menu. Don't assume WPML did it.

Trap 2 — menus created over the API land in the wrong language

Create a nav_menu term via REST and it is born in the default language. WPML then silently strips every item in it that points at another language's page. The menu saves, the API lists the items back to you, and the front end renders nothing.

Fix: set the term's language before filling it. We added a route for exactly this:

POST /wp-json/wpbuddy/v1/set-term-language
{ "term_id": 1091, "taxonomy": "nav_menu", "language": "zh-hant" }

Menus created by hand in wp-admin already carry the right language and are unaffected.

Content gaps you'll run into

AreaStatus

So zh-hk and zh-cn menus are mostly showing fallback links today. That is known, not a bug you need to fix on sight — but it's why those languages look thin.

Rules of thumb

  • Always know which language you're editing. The URL prefix tells you.
  • A page is not "translated" until WPML links it to its original — a standalone page in another language is invisible to the switcher.
  • English copy runs ~30–40% longer than Chinese for the same meaning. Type sizes are tuned down for EN. Check both.
  • If a language renders empty where another renders fine, suspect the cache first (section 11), then WPML.

07Menus & navigation

The header is a WordPress menu wearing an ElementsKit costume. Once that clicks, the mega menu stops being mysterious.

How the mega menu is actually built

The header is a normal WP menu. ElementsKit marks a top-level item as a mega-menu parent and attaches a separate Elementor document to it, which renders as the dropdown panel:

<li class="… elementskit-megamenu-has">
  <a>Solutions</a>
  <div class="elementskit-megamenu-panel" id="ekit-megamenu-panel-{itemID}">
      ← a whole Elementor post (type: elementskit_content)
  </div>
</li>

So "edit the mega menu" means two different jobs: the item is in Appearance → Menus, the panel is an Elementor template.

The newer, menu-driven approach

Hardcoding 24 links into a panel × 4 languages doesn't scale. New preview pages render navigation from a real WP menu with one shortcode:

[wpbuddy_nav menu="mega-solutions"   depth="2" icons="label"]
[wpbuddy_nav menu="footer-resources" depth="1"]
[wpbuddy_nav menu="footer-social"    depth="1" icons="1"]

You give it the base slug; it appends the language suffix automatically — -zh, -hk, -cn — so one page template serves all four languages. If a language has no menu it renders nothing, on purpose: an empty column is an honest signal that a menu still needs building, whereas a silent English fallback is how zh-hk once shipped an English header.

08Building a page

The native-HTML route, where most of your frontend work will happen. These patterns are battle-tested — use them before inventing your own.

Full-bleed layout — the #1 recurring issue

With Elementor off, the page renders through Hello Elementor, whose main.site-main boxes content to 1140px and adds a top gap. Elementor sections used to break out of that; raw HTML doesn't, so you get grey strips down both sides.

Every native page carries a page-specific, unscoped override. Inline <style> only loads on that page, so it's safe:

main.site-main{max-width:none!important;margin:0!important;padding:0!important;width:100%!important}
main.site-main>.page-content{max-width:none!important;margin:0!important;padding:0!important}
.page-content>p:empty{display:none!important;margin:0!important;height:0!important}

That last rule kills the empty paragraph wpautop inserts at the top. Also strip the content and collapse whitespace between tags before pushing, so wpautop has nothing to chew on.

Backgrounds

A section background goes on the full-width <section>, never on an inner max-width .wrap — otherwise white strips show at both edges. Pattern: section carries the background, inner .wrap (max-width 1180, margin:0 auto, padding:0 28px) centres the content.

Centring a button

Use a text-align:center wrapper. The theme overrides both align-self:center and auto-margins on flex children — both failed silently in production.

<div class="cta"><a class="btn">了解更多</a></div>

.cta{text-align:center;margin-top:auto}  /* centre + pin to bottom of flex column */
.btn{display:inline-block}               /* stays inline-block so text-align works */

That margin-top:auto also gives you Elementor-style equal-height cards: image at the top, button pinned to the bottom, regardless of how long the copy is.

Figma-exported pages

Some pages come straight out of Figma as a fixed 1440px canvas with every element absolutely positioned. They scale down with a --hp-scale variable.

Known failure mode

The stylesheet reads --hp-scale but nothing sets it, so below 1440px the canvas gets clipped at the right edge. Any such page needs a small script that measures the container and sets the variable. If a design page is cut off on your laptop, this is why.

And a judgement call worth internalising: a Figma design with 20 fixed slots cannot hold 24 real items. When real content outgrows a fixed layout, convert it to a flowing one (grid + shortcode) rather than squeezing or dropping items. We did exactly that to the Solutions panel.

Images and assets

  • Deduplicate Figma images by fills[].imageRef, not by layer name — designers reuse names while each fill is a distinct image.
  • Upload to the media library with curl. Python's urllib gets 403'd by the WAF unless you send a browser/curl User-Agent.
  • A reused filename gets a -1 suffix — check the URL you got back, don't assume.

09Design system

Navy and orange. The contrast rules below are computed, not opinions — please don't quietly break them.

TokenHexUse
Navy#1B365DHeadings, dark sections, ink
Orange#FF9E1BPrimary CTA fill, accents
Green#12BF6DHover, success
Body gray#4D4D4DBody copy
Blue#4285F4 / #1A73E8Links, card titles
Border#EAEDF2Card borders, dividers
The orange is a fill, not an ink

Orange text on a light background is 1.90:1 — unreadable. Never use it for text, a thin line, or an icon on white. Navy on an orange fill is 5.86:1 and is the correct usage. White on orange is 2.07:1 and is never correct.

Type

Raleway across the site, Arial fallback. Hero H1 50px desktop / 32px mobile at weight 900; H2 36/24 at 800; body 16–18px. Sizes come from clamp-based tokens in :root — --fs-h1, --fs-h2, --fs-lead, --fs-body — so set the token, don't hardcode a px value in a rule.

Cards

Floating white cards, not flat-bordered: 12px radius, 24–32px padding, soft shadow (0 6px 24px rgba(16,40,80,.10)) that deepens and lifts 4px on hover. The image sits inset on a light-blue panel with its own 10px radius — not bleeding to the card edge. Title centred and brand-blue, body left-aligned and grey.

Layout

  • Container max-width:1140px, padding:0 20px
  • Section padding 80px desktop / 60px mobile
  • Fixed transparent header, 90px desktop / ~70px mobile — every hero needs a dark background or overlay, or the white header text vanishes

The live tokens also sit in wp-admin under WP Buddy → Brand Kit.

Accessibility we hold ourselves to

  • Never encode meaning by colour alone — add a shape, a glyph, or a label. Roughly one man in twelve has a red–green deficiency.
  • Anything clickable shows a pointer cursor, including the little arrow glyphs beside menu text. They're separate elements and are easy to miss.
  • Check desktop and mobile on every change. Not optional.

10Figma & Claude → WordPress

A lot of pages here are built with Claude rather than by hand. This is how you get in, and which of the two routes you're on.

Signing in to Claude

We use a shared mc-marketing Claude account for this work — not a personal one, so that projects, skills and history stay with the team.

  1. Go to magic.mcai.dev and sign in with your Master Concept Google account.
  2. Find the mc-marketing tile and use it to sign in to Claude. Magic Login holds the password and the one-time code.
  3. That's it — no password ever gets copied into a file, a note, or a chat.
What Magic Login is

An internal single page that reads the team's shared logins out of 1Password at the moment you open it. Sign-in is your own Workspace identity, so access can be granted and revoked per person. If a tile is missing, ask Tommy to add it rather than looking for the password elsewhere.

Route A — Figma → WordPress yours

This is the technical route, and the one you'll live in. The figma-to-wp skill drives it:

  • Pulls the frame's render, its copy verbatim, its colour and type tokens, its box geometry and its images out of Figma.
  • You then write the HTML against those real numbers, one section at a time — the skill does not generate the page for you.
  • verify confirms every string survived and the site's hard rules hold · audit names which element is wrong and by how much · diff screenshots the result and scores each section against the Figma render · mobile runs the phone checks the frame can't answer.
  • Then it uploads the media and creates the page as a draft, with the right slug and Permalink Manager URI.
  • pull goes the other way — start from a page that already exists in WordPress.

Figma is read through its API with a read-only token — ask Tommy to set it up for you rather than minting your own. Nothing publishes itself; a draft is always the end state until someone says otherwise.

This is the route, not an option

New pages are built this way now — see the direction note in section 1. If a design arrives and your instinct is to rebuild it in Elementor, that's the habit we're moving away from.

Route B — Claude Design → WordPress colleagues

Non-technical colleagues build a page in Claude Design and hand over a link; Claude publishes it. You should know this route exists because you will be the one who fixes it when the result needs a human.

Read the guide we give colleagues

It's one page covering what they send, page vs post, which language, category and region, cover image and SEO, the web address, and where it sits in the menu. Worth ten minutes — it's the shared vocabulary everyone here uses when they ask for a page.

Same rules either way

Both routes end in the same WordPress, with the same cache, the same four languages and the same no-revisions rule. Nothing about using Claude changes sections 4, 6 or 11.

11Deploy & verify

Two different pipelines depending on what you changed — and one cache that will lie to you.

Plugin code → git

  1. Edit under plugin/
  2. php -l <file> — CI doesn't lint yet
  3. Bump WPBUDDY_VERSION and add a changelog line in wp-buddy.php for anything user-facing
  4. Commit → push to main
  5. GitHub Actions syncs plugin/ → wp-content/plugins/wp-buddy/ on the live site

Watch it land: gh run list --repo mcailab/wpbuddy — or the Actions tab. No FTP, no server login; the push is the deploy.

Page content → REST

Pages are pushed as raw HTML via the REST API using a dedicated user that holds unfiltered_html. The plugin exposes named abilities for the fiddly parts:

AbilityDoes
mc/set-post-htmlWrite raw HTML into a post without KSES stripping it
mc/create-localized-pageCreate a page in a given WPML language, optionally linked as a translation
mc/regenerate-permalinkRebuild the Permalink Manager URI after a slug change
mc/find-postsSearch posts/pages across languages
mc/set-language · mc/set-terms · mc/get-meta · mc/brand-guideLanguage assignment, taxonomy, metadata, brand tokens
The cache will lie to you

SiteGround full-page-caches for logged-out visitors and Cloudflare sits in front of that. A change can be live and still invisible in an incognito window for minutes.

  • Query strings do not bust the SiteGround page cache. ?bust=1 is not a test.
  • Logged-in (admin) views bypass the cache — which is why it "works for you" and not for anyone else.
  • Clear it properly with 清除 SG 快取 in the admin bar. Re-saving a page also purges that page.
  • Check response headers x-proxy-cache and cf-cache-status to see which layer served you.
Verify by DOM, not by eyeball

Screenshots show stale renders. To confirm a change truly landed, read the live DOM or computed style — fetch the page and grep for your markup, or use getBoundingClientRect / computed CSS in the console. Pixels can be cached; the parsed DOM you just fetched cannot.

Preferred workflow

Edit local → review local → push to prod → verify via DOM. Reviewing locally first avoids the entire cache problem, which is why we do it that way round.

12Gotchas

Every one of these has already cost someone here real time. Skim now; come back when something behaves impossibly.

SymptomCause & fix
REST response isn't valid JSONElementor injects <style> blocks into REST responses. Parse from after the last </style>.
Python HTTP call returns 403, curl worksThe WAF blocks the default urllib user-agent. Send a browser or curl/8 User-Agent.
Menu saves, API lists items, front end is emptyWPML stripped cross-language items from a menu created in the wrong language. Section 6, trap 2.
One language looks broken, the others are fineAlmost always the page cache. Confirm before debugging anything else.

13House rules

Short list. Mostly about not surprising the next person.

Code

  • Match the surrounding code — its naming, its comment density, its idiom. Don't import a different house style into one file.
  • Names are canonical and domain-free: no leaking one customer's or one page's vocabulary into shared code.
  • Reusable dynamic content → a shortcode. Never four hardcoded copies, one per language.
  • php -l before you commit.
  • Bump the version and write the changelog line for anything user-facing.

Working on production

  • Back up the current HTML of any page before you overwrite it.
  • Review locally first.
  • Verify by DOM after pushing.
  • If you changed something and can't see it, suspect cache before you suspect your code — then suspect your code.

Asking

Ask early about: anything touching the live header or footer, anything that changes a URL, anything multilingual you're unsure about, and anything that needs a credential. None of those are things to figure out quietly on production.

2 · Asana — the team board today

Open the Asana board

Where the wider team's work is tracked today. Requests from the business arrive through Asana Forms rather than as ad-hoc messages — someone fills in the form, it lands on the board as a card with the details already structured. If a colleague asks you for something in chat, the right answer is usually "put it through the form", so it's tracked and nobody loses it.

3 · Wilco → Plane — where we're heading the goal

This is the workflow automation we're building toward, and it's already running on this site. It removes the retyping step entirely:

  1. Someone spots a problem on a live page and pins feedback directly on it — on the page itself, not in a ticket describing the page.
  2. Wilco captures the pin with its page, its position, the device, the author and any screenshot.
  3. One action turns it into a work item in Plane — MC-1, MC-4, MC-5 and so on — tracked, assignable, closable.
  4. Any pin reopens the real page with the pin in place via ?fb=<id>, so you see exactly what they saw.

Four projects are wired up: Master Concept Website, ATS (careers), EIP and Aptitude Test. The website currently has 3 open pins, all already linked to Plane items.

Same story as Elementor → HTML

Asana is what we use today; Wilco + Plane is the end state. Don't treat the overlap as confusion — it's a migration in progress, the same as section 1's. When in doubt about where something belongs, ask rather than opening a fourth place to track work.
